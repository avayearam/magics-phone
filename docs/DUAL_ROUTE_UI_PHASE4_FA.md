# Magic Phone — فاز ۴: کنترل دو مسیر صوتی در رابط وب

تاریخ: ۲۰۲۶-۱۱-۱۸

## تصمیم‌های محصول

- اتصال به **Magic Core** همچنان خارج از محدوده است؛ در این فاز هیچ ارتباط خارجی یا احراز هویت Core پیاده‌سازی نشده است.
- نسخه پنل وب: **0.4.0**؛ موتور Agent بومی همچنان **0.3.0** است و از همان قرارداد موجود استفاده می‌کند.
- سوابق `history/` دست‌نخورده می‌مانند. تنظیم صوت Chrome و Phone Link روی سیستم کاربر تغییر داده نمی‌شود.

## تغییرات اجرایی

1. هر دو اسلات Backend، یعنی **A** و **B**، اکنون کنترل مستقل در UI دارند: نوع مبدأ (Input یا Loopback)، دستگاه مبدأ، دستگاه مقصد، شروع، توقف و نمایش وضعیت خود مسیر.
2. دکمه **توقف هر دو مسیر** فقط درخواست توقف اسلات‌هایی را ارسال می‌کند که در وضعیت `running` یا `starting` هستند. درخواست‌ها به Endpoint موجود `/api/route/stop` ارسال می‌شوند؛ برای این قابلیت API جدید یا رفتار دائمی پس‌زمینه ساخته نشده است. اگر یکی از توقف‌ها شکست بخورد، به‌عنوان توقف موفق گزارش نمی‌شود.
3. از انتخاب مقصد مشترک دو مسیر فعال، مسیر برگشتی مستقیم Loopback و مبدأ/مقصد یکسان، علاوه بر کنترل موجود Backend، در UI هم جلوگیری می‌شود. **این محافظت همه انواع فیدبک فیزیکی را پوشش نمی‌دهد**.
4. پس از شروع هر مسیر، فیلدهای پیکربندی آن تا توقف قفل می‌شوند. اگر صفحه دوباره باز شود و مسیر از قبل فعال باشد، پس از دریافت وضعیت و شناسایی دستگاه‌ها مشخصات مسیر واقعی بازسازی می‌شوند.
5. تنظیم‌های انتخاب دستگاه و تم **فقط در localStorage همان مرورگر** حفظ می‌شوند. توکن کنترل Agent در localStorage ذخیره نمی‌شود. هیچ مسیر صوتی با بارگذاری پنل به‌صورت خودکار فعال نمی‌شود.
6. نام دستگاه و پردازش از طریق `textContent` نمایش داده می‌شود، نه HTML تزریقی.
7. در صورت قطع ارتباط با Agent، وضعیت مسیرها نامعلوم تلقی و کلیدهای شروع غیرفعال می‌شوند؛ اعلام موفقیت جعلی انجام نمی‌شود.

## آنچه هنوز انجام نشده

- تست اجرای واقعی این رابط بر روی Windows x64 با موتور WASAPI و دستگاه‌های کاربر؛
- تفکیک صدای یک برنامه از ترکیب صوت کل یک دستگاه (Application Loopback)؛
- بازنمونه‌برداری برای نرخ‌ها/فرمت‌های متفاوت، اصلاح Clock Drift، مدیریت تغییر سخت‌افزار یا فیدبک فیزیکی؛
- تزریق ورودی میکروفون به برنامه هدف بدون درایور مجازی سازگار؛
- فایل نصب نهایی، امضای دیجیتال و تأیید امنیتی Defender.

**دو اسلات مستقل یک‌طرفه** به معنای «برقراری ارتباط اختصاصی و تأییدشده دوطرفه بین Chrome و Phone Link» نیست؛ ادعای اخیر فقط پس از تست صوت واقعی معتبر است.

## تست‌های انجام‌شده در همین فاز

- `node app/web/dual-route.test.cjs`: موفق؛ تست شبیه‌سازی ۱) عدم شروع خودکار، ۲) ممنوعیت شروع در حالت غیرفعال، ۳) تشخیص دستگاه، ۴) شروع مستقل A/B، ۵) مقصد مشترک، ۶) حلقه Loopback، ۷) قفل تنظیمات مسیر فعال، ۸) توقف هر دو، ۹) شکست توقف و گزارش عدم تأیید، ۱۰) قطع شبکه و مسدودسازی شروع، ۱۱) ذخیره انتخاب‌ها، ۱۲) تم و ۱۳) نمایش امن نام دستگاه.
- اعتبارسنجی HTML با Python `html.parser`: شناسه‌های یکتا و ارجاع درست Labelها — موفق.
- تست واقعی Chromium در محیط اجرای فعلی: **تکمیل نشد (Timeout)**. بنابراین هیچ تأیید ظاهری یا عملکردی روی مرورگر ویندوز اعلام نمی‌شود.
- موتور Go در این فاز تغییری نکرده است؛ نتایج قبلی ساخت آن مربوط به فاز ۳ است، نه آزمایش مجدد این مرحله.

## مسیر بعد

پیش از انتشار نصب‌کننده یا فعال کردن انتقال به‌صورت پیش‌فرض، موتور 0.3 باید روی ویندوز با دستگاه‌های واقعی آزمایش شود؛ سپس معماری تفکیک صدای برنامه و انتقال آن به ورودی برنامه هدف تکمیل شود. تا آن زمان فعال‌سازی آزمایشی Backend به همان تنظیم صریح توسعه‌دهنده محدود است.
